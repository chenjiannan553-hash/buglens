# 架构说明

## 一句话

一个单向数据流的 CLI：**参数 → 校验 → 领域规则 → 存储 → 渲染**。没有中间层，没有依赖注入容器，没有插件系统。

---

## 分层

```
┌─────────────────────────────────────────────┐
│  cli.py          参数解析、输出格式、退出码  │
└──────────────────┬──────────────────────────┘
                   │  只调用领域函数，不写 SQL
┌──────────────────▼──────────────────────────┐
│  validator.py   结构校验                     │
│  state_machine.py  流转规则                  │
│  gate.py        门禁判定                     │
│  dedupe.py      相似度                       │
│  stats.py       聚合                         │
└──────────────────┬──────────────────────────┘
                   │  纯函数，不碰 IO
┌──────────────────▼──────────────────────────┐
│  db.py          唯一的数据访问层             │
│  models.py      数据结构                     │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  SQLite 单文件                               │
└─────────────────────────────────────────────┘

  渲染旁路：report.py（md/csv/html）、table.py（终端表格）、web.py（服务）
  数据旁路：importer.py（解析）、demo.py（示例）
```

**硬约束：除 `db.py` 外，任何模块都不 import sqlite3。** 换存储只需改一个文件。

## 关键设计决策

### 1. 校验为什么放在入库前而不是入库后

大部分工具是"先存下来，有问题后面再说"。buglens 反过来：**不合规的数据不进库**。

代价是录入摩擦变大，收益是库里永远没有"待补充"这种脏状态。对一个要把门禁建立在数据之上的工具，这个取舍没得选——你没法在一个 30% 记录缺复现步骤的库里判断 S1 是否清零。

### 2. 为什么错误要一次报全

早期版本是遇到第一个缺失就 `return`。实际用起来，用户要来回改 5 次才能录一条缺陷。改成收集式校验后，一次报完所有问题。

实现上有个细节：缺失的字段跳过长度检查，避免同时报"缺少 env"和"env 过短"两条重复信息。

### 3. 状态机为什么用显式表而不是守卫函数

```python
TRANSITIONS = {
    "new": {"triaged", "closed", "reopened"},
    ...
}
```

表驱动的三个好处：
- 合法的流转可以**被程序枚举**（`allowed_targets()` 直接用于错误提示）
- 加状态只改数据，不改逻辑
- 测试可以对整张表做穷举

如果写成 `if` 链，错误提示里的"可选目标"就只能硬编码一份，两份必然会漂移。

### 4. 门禁为什么要有退出码

门禁的价值不在于打印一段漂亮的报告，而在于**能被自动化系统判定**。所以：

- `gate` 通过返回 0，阻断返回 1
- `add` 校验失败返回 2，疑似重复返回 3

这套码表让 shell 的 `||` 和 CI 的 step 都能直接用。

### 5. 为什么 `verified → in_progress` 是禁止的

已验证的缺陷重新出现，语义上是**复发**，应该走 `reopened`。如果允许回到 `in_progress`，统计上就分不清"新发现的 S1"和"老问题又来了"——而这两个信号对质量趋势的判断完全不同。

### 6. 查重的权重为什么是 55/30/15

基于一个朴素假设：**标题最接近缺陷本质，步骤次之，实际结果再次之**。

标题是经过人工提炼的一句话；步骤容易因复制模板而高度雷同（比如所有"登录"类缺陷的步骤都长得差不多）；实际结果往往只有几个字。所以标题权重最高。

同模块 +5%、同级别 +3% 是弱信号，只用来在分数接近时做排序微调，不足以单独触发命中。

### 7. 终端表格为什么自己实现

`str.ljust()` 按字符数补齐，中文占两个终端列宽，直接用它表格必然错位。`table.py` 用 `unicodedata.east_asian_width()` 计算显示宽度，宽字符（W/F）算 2 列。

这是个很小的实现，但它决定了 CLI 输出能不能看。

### 8. Web 看板为什么不用 Flask

看板是只读的、单页的、没有交互。用 `http.server` 十几行就能覆盖，引入框架会让"pip 之外克隆即可运行"的承诺破产。

HTML 里的 CSS 全部内联，不引任何外部资源，所以导出的文件可以直接微信发给别人，对方离线也能打开。

## 数据流举例：`buglens add`

```
argv
 └─► build_parser() 解析成 Namespace
      └─► cmd_add()
           ├─ 组装 dict
           ├─ validator.validate_or_raise()   ← 失败 → 打印错误，exit 2
           ├─ Bug(**cleaned)
           ├─ dedupe.find_similar()           ← 命中 → 提示，exit 3（除非 --force）
           ├─ Store.add_bug()
           │    ├─ INSERT bugs
           │    └─ INSERT history (from=None, to=new)
           └─ print "[OK] 已创建缺陷 #N"
```

## 测试策略

118 个单测，分四层：

| 文件 | 覆盖 | 特点 |
| --- | --- | --- |
| `test_validator.py` | 校验边界 | 每个规则都有正反两个用例 |
| `test_state_machine.py` | 流转表 | 对全表穷举 + 非法路径 |
| `test_db.py` | 持久化 | 每个用例独立临时库，含跨连接持久化验证 |
| `test_core.py` | 查重/门禁/报表/导入 | 纯函数，无 IO |
| `test_cli.py` | 端到端 | 真实走 argparse，断言退出码 |

CLI 测试的写法值得说明：它不 mock，直接 `main([...])` 然后用 `redirect_stdout` 捕获输出。**断言的是退出码和用户真正看到的文字**，而不是内部函数调用次数。这样重构内部实现时测试不会误报。

CI 在 ubuntu / macos / windows × Python 3.9 / 3.11 / 3.13 上跑，共 9 个组合。

## 如果还要长大

按优先级：

1. **并发写** — 加 `PRAGMA journal_mode=WAL` + 指数退避重试
2. **语义查重** — 现在是字符串相似度，接 embedding 能捞到措辞不同的重复项
3. **附件** — 缺陷截图目前只能贴链接，可以存到 `blobs/` 目录并记录哈希
4. **多用户** — 需要真的鉴权，但那意味着要引入服务端，和"单文件"的定位冲突

第 4 条大概率不会做。工具一旦需要部署，就再也不会被随手用起来了。
